# 🤖 AI Disclosure

Documento de transparencia sobre el uso de herramientas de Inteligencia Artificial generativa durante el diseño, arquitectura, desarrollo y documentación de la prueba técnica **Alegra Restaurant**.

Para cada fase e ítem del proyecto se detalla de forma explícita qué se le solicitó a la IA, qué sugerencias se conservaron tal cual, qué propuestas fueron corregidas o descartadas (con su justificación técnica), y qué componentes fueron concebidos e implementados enteramente sin asistencia de IA.

**Herramientas utilizadas:** Asistentes de IA generativa (modelos conversacionales de lenguaje de última generación) utilizados como copilotos de consulta puntual para sintaxis de especificaciones (Mermaid), generación de esqueletos (scaffolding) de código repetitivo y redacción base de documentación. No se utilizó generación ciega, no supervisada ni ejecución desatendida; todo el código y decisiones arquitectónicas fueron validados, auditados y refinados manualmente.

| Ítem | Prompts (resumen) | Conservado tal cual | Corregido / descartado y por que | Hecho sin IA |
|:---|:---|:---|:---|:---|
| **Gateway Service (`services/gateway`)** | *"Dame un esqueleto base en TypeScript para un servidor HTTP usando únicamente el módulo nativo node:http (sin Express) que permita rutear por método y URL y parsear el body JSON de un request."* | La estructura base del listener de `createServer`, la acumulación de chunks de datos en streams (`req.on('data')`, `req.on('end')`) y la inicialización del servidor WebSocket con la librería `ws`. | **Corregí el manejo de errores y seguridad de respuestas:** La IA implementó un router con callbacks anidados que capturaba excepciones devolviendo detalles internos de la pila (stack trace en 500). Lo reemplacé por una arquitectura de funciones controladas con cabeceras CORS manuales, validación de schemas de entrada, respuestas tipadas y códigos HTTP semánticos (200, 201, 202, 400, 404, 500). También corregí el bridge de NATS a WebSockets para evitar duplicación de emisiones. | El enrutamiento modular de los 8 endpoints REST (`/health`, `/api/orders`, `/api/orders/:id`, `/api/warehouse/inventory`, `/api/kitchen/recipes`, `/api/stats`, `/api/purchases`), el pool de base de datos (`pg.Pool`), y la gestión del ciclo de vida de los clientes WebSocket conectados con filtrado seguro de eventos. |
| **Warehouse Service & Concurrencia (`services/warehouse`)** | *"¿Cómo estructurar un cliente HTTP con fetch nativo de Node.js 20 para consultar un endpoint externo con timeout controlado?"* | El cliente de petición HTTP básico en `market-client.ts` con manejo de query parameters para `https://recruitment.alegra.com/api/farmers-market/buy?ingredient={name}`. | **CORRECCIÓN CRÍTICA DE RACE CONDITION:** La IA generó originalmente una consulta simple `SELECT stock` seguida de una validación en código JavaScript y un posterior `UPDATE stock`. En escenarios con múltiples órdenes concurrentes solicitando hamburguesas simultáneamente, esto causaba lecturas sucias y dejaba el inventario en números negativos. **Descarté completamente ese enfoque** e implementé una transacción explícita (`BEGIN ... COMMIT`) con bloqueo pesimista `SELECT ... FOR UPDATE` sobre la fila del ingrediente, sumado a un descuento condicional atómico `UPDATE ingredients SET stock = stock - $1 WHERE id = $2 AND stock >= $1 RETURNING stock`. Además, la IA lanzaba una excepción fatal cuando la plaza de mercado devolvía `quantitySold: 0`; lo corregí implementando un bucle de reintentos con backoff controlado de 500ms y registro de compras fallidas/exitosas en `purchase_history`. | Toda la lógica de negocio transaccional del almacén, el cálculo de déficits por ingrediente, el algoritmo de reabastecimiento en la plaza de mercado, la emisión de eventos de inventario (`inventory.updated`, `ingredients.purchased`, `ingredients.ready`) y el manejo de excepciones tipadas (`ServiceError`). |
| **Orders & Kitchen Services (`services/orders`, `services/kitchen`)** | *"¿Cómo suscribir un manejador a un tópico de NATS usando la librería oficial nats de npm y decodificar el payload con JSONCodec?"* | El patrón de suscripción iterativa sobre mensajes NATS (`subscription`) y la deserialización con `JSONCodec().decode(msg.data)`. | **Corregí la saturación del broker (Staggering):** Al crear una orden de varios platos (ej. 10 platos), la IA generaba todos los eventos `order.cook` de golpe en paralelo instantáneo. Esto saturaba la bodega antes de que pudiera responder. Implementé un despacho escalonado (*staggering*) con retardo de 200ms entre platos para simular el ritmo real de una cocina. En Kitchen, la IA seleccionaba recetas con un array estático en memoria; lo cambié por una consulta SQL dinámica `ORDER BY RANDOM() LIMIT 1` contra PostgreSQL para garantizar variedad real de recetas. | La gestión del ciclo de vida de la orden, el conteo atómico de platos completados (`completed_plates = completed_plates + 1`), la transición automática de la orden a `COMPLETED` cuando todos los platos terminan, y la simulación controlada del tiempo de cocción (1 a 3 segundos aleatorios) antes de emitir `plate.completed`. |
| **Contenerización Docker (`Dockerfile` y `docker-compose.yml`)** | *"Escribe un Dockerfile multi-stage para un microservicio Node.js TypeScript que compile el código con tsc y ejecute solo la carpeta dist en producción."* | El patrón multi-stage (`builder` con dependencias completas y `production` con solo dependencias de producción) para reducir el peso de las imágenes. | **Corregí los Healthchecks y orden de dependencias:** La IA no incluía healthchecks reales para PostgreSQL ni NATS, lo que causaba que los microservicios intentaran conectarse antes de que la BD estuviera lista y se cayeran al iniciar (`crash loop`). Agregué `pg_isready` y comprobaciones HTTP en el puerto `8222` de NATS con condiciones `service_healthy` en `docker-compose.yml`. | La configuración completa de redes (`alegra-network`), volúmenes persistentes (`postgres_data`), inyección de variables de entorno compartidas y puertos de monitoreo de NATS. |
| **Punto Bonus IA: Módulo de Copilot y Simulación (`ai-service.ts`)** | *"Estructura un cliente HTTP ligero sin librerías para consultar la API de Groq o OpenAI pasando un prompt con contexto estructurado del restaurante."* | La sintaxis del payload para los endpoints de chat completions y la plantilla de inyección de prompt. | **Corregí el riesgo de fallo si no hay API Key:** La IA asumía que el evaluador siempre tendría una API Key configurada. Si alguien clonaba el repo sin credenciales, la app fallaba con error 401. Diseñé e implementé el motor heurístico local (*Zero-Config Fallback*) que analiza la telemetría viva de PostgreSQL y genera respuestas y diagnósticos completos sin depender de servicios externos. | Toda la matemática y lógica del simulador de demanda masiva (cálculo de frecuencias estocásticas de las 6 recetas, proyección de consumo, cálculo de cuellos de botella y estimación de compras a la plaza de mercado). |

## 🎯 Conclusión y Filosofía de Uso de IA

El uso de Inteligencia Artificial en esta prueba técnica fue abordado bajo una premisa clara: **la IA es un multiplicador de productividad, no un sustituto del criterio de ingeniería de software.** 

Las decisiones críticas del proyecto —como garantizar la consistencia transaccional del inventario frente a condiciones de carrera, evitar frameworks en cumplimiento estricto del enunciado, seleccionar NATS sobre brokers pesados para mantener un footprint mínimo, y diseñar una experiencia de usuario sobria y funcional— fueron concebidas y ejecutadas desde la experiencia técnica humana.
